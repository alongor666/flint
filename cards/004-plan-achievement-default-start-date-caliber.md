## 原文

（2026-10-15，与 001 修订同句下达）KPI 看板 保费/件数/增长率/达成率六列墙卡 变更为默认"起保口径"，计划达成变更为默认"起保口径"

## 澄清（AUQ）

### 先探可定（依据）

- 计划达成端点 `/plan-achievement`（`server/src/routes/query/premium-plan.ts:210`）参数 schema **无 dateField**，无法口径切换。
- SQL 全部读 `achievement_cache` 预聚合表（启动时 `buildAchievementView()` 预构建，`server/src/sql/premiumPlan.ts:5,15`）——签单口径**固化在缓存构建层**：time_progress 锚定数据内最新签单日、月进度月锚、跨年签单剔除、团队分子分母同批人（25 补充①+owner 2026-10-04）等语义全部按签单日书写。
- 改动面：缓存层双口径重建（预计算签单+起保两套）或直查 PolicyFact 绕缓存（性能成本，扇出限流 PR #239 教训：两并发重查询即触 2048MB 上限）——实现路径转正探索定，不预设。
- 计划数口径事实：organization_plan 计划按签单口径制定（sx 整体达成注释「全省签单保费」`server/src/sql/kpi.ts:272`；达成率=实际÷计划×时间进度）。

### 待 owner 裁定（AUQ）

- Q1 实际保费改起保后，计划数仍为签单口径计划——达成率将系统性偏低（起保滞后签单，年末最大），是否接受？ 选项: A 接受偏移（推荐，达成率语义改「有效口径达成」）/ B 计划达成维持签单（撤回本卡）/ C 计划数同步换算起保口径 → **待答**
- Q2 经营体检（/health-check）与 KPI 走势线（sparklines 周演进族）与六列同源的达成率/增长率指标，dateField 默认是否同步起保？ 选项: A 同步（推荐，口径单一事实源，防看板与体检数字打架）/ B 保持签单（两处数字将不一致）→ **待答**

## 讨论

- 与 001 同族（业绩墙卡指标默认口径改起保），001 的六列部分因 SQL 已消费 dateField 改动轻；本卡因 achievement_cache 架构改动重——转正映射建议：两卡并一个 issue（「业绩墙卡与计划达成默认起保口径」），PR 可按 001（轻）/003（重）拆两支。

## 探索 #1（2026-10-15）

- 探查锚: chexian-api @ 61063382（origin/main，2026-10-15）
- 防撞车: 开放 issue 无撞车（#1321 机构层达成率归属是另一维度——出单机构 vs 花名册归属，不冲突但同页，实施时留意）。
- 实施要点:
  - achievement_cache 双口径：buildAchievementView 预计算扩为签单/起保两套（或缓存表加口径维度列），查询侧按口径选表/选列；月进度、time_progress、跨年剔除、团队同批人语义逐条按起保日语义重写对拍。
  - 路由 schema 加 dateField（默认 insurance_start_date，可切签单与否随 Q1 裁定）；
  - 前端计划达成页（reports 域）默认传起保；
  - KPI 六列内嵌达成率（kpi SQL 的 vehicle_plan CTE）随 001 的 dateField 自动切换，与计划达成页数字需对拍一致；
  - 风险：缓存构建时长与内存翻倍（PR #239 扇出限流先例）；起保口径下「数据内最新起保日」锚与计划年的时间进度分母错位（时间进度锚签单日书写，需重定义）。
- 转正映射建议: 与 001 并一个 issue，PR 拆两支（001 轻 / 003 重）。
- 验收: 计划达成页与 KPI 达成率列口径对拍一致；签单/起保切换（如保留）数字正确；buildAchievementView 双口径构建通过 governance；既有计划达成测试族通过。
